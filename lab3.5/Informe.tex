\subsection{Actividad 6.1: Servidor de control remoto (socket server)}
\textit{Enunciado: Implemente un código de Processing que act\'{u}e como servidor TCP.
El servidor debe recibir comandos de \'{a}ngulos enviados desde un cliente remoto y retransmitirlos
al servo f\'{i}sico. }

Processing trae incluida la librer\'{i}a \texttt{processing.net}, que permite montar servidores
y clientes TCP sin instalar nada extra~\cite{procnet}. Para esta actividad se creó un objeto
\texttt{Server} escuchando en el puerto~12345 (C\'{o}digo~\ref{lst:srv_setup}), mientras que
el servo queda configurado en el pin~3 en modo \texttt{Arduino.SERVO} con una posici\'{o}n
inicial de $90^\circ$.

\begin{lstlisting}[language=Java,
    caption={Inicializaci\'{o}n del servidor TCP y del servo en \texttt{setup()}.},
    label={lst:srv_setup},
    float=ht!]
import processing.serial.*;
import processing.net.*;
import cc.arduino.*;

Arduino arduino;
Server miServidor;
int servoPin   = 3;
int anguloServo = 90;

arduino = new Arduino(this, Arduino.list()[2], 57600);
arduino.pinMode(servoPin, Arduino.SERVO);
arduino.servoWrite(servoPin, anguloServo);

miServidor = new Server(this, 12345);
\end{lstlisting}

Lo primero que se hizo fue armar el circuito conectando el servomotor a uno de los pines
digitales con soporte PWM de la placa, tal como se ve en la Figura~\ref{fig:circuito_act1}.

\begin{figure}[ht!]
    \centering
    \includegraphics[width=0.8\linewidth]{img/circuito_act1.jpg}
    \caption{Conexión del servomotor al pin digital del microcontrolador.}
    \label{fig:circuito_act1}
\end{figure}

\pagebreak

En \texttt{draw()}, el servidor revisa si hay alg\'{u}n cliente con datos disponibles usando
\texttt{miServidor.available()}. Cuando los hay, lee la cadena hasta encontrar el car\'{a}cter
\texttt{'\textbackslash n'} que el cliente agrega al final de cada comando. Ese delimitador es
necesario porque TCP no tiene bordes de mensaje, sin \'{e}l no habr\'{i}a forma de saber
d\'{o}nde termina un valor y d\'{o}nde empieza el siguiente (C\'{o}digo~\ref{lst:srv_draw}).

Validar que el valor est\'{e} en el rango $[0,\,180]$ antes de llamar a \texttt{servoWrite()}
es importante para proteger el hardware, un valor fuera de ese rango puede da\~{n}ar el servo
mec\'{a}nicamente o producir una se\~{n}al PWM incorrecta.

\begin{lstlisting}[language=Java,
    caption={Recepci\'{o}n, validaci\'{o}n y aplicaci\'{o}n del \'{a}ngulo en \texttt{draw()}.},
    label={lst:srv_draw},
    float=ht!]
Client clienteEntrante = miServidor.available();

if (clienteEntrante != null) {
    String cadena = clienteEntrante.readStringUntil('\n');

    if (cadena != null) {
        cadena = trim(cadena);
        try {
            int nuevoAngulo = int(cadena);
            if (nuevoAngulo >= 0 && nuevoAngulo <= 180) {
                anguloServo = nuevoAngulo;
                arduino.servoWrite(servoPin, anguloServo);
            }
        } catch (Exception e) {
            println("Error de trama: " + e.getMessage());
        }
    }
}
\end{lstlisting}

\pagebreak

En la Figura~\ref{fig:resultado_act2} se puede ver el servo siendo controlado desde otra máquina
distinta a la que tenía el Arduino. Otro grupo actuó como consola de control con la
interfaz gráfica, mientras el hardware respondía en tiempo real.
\begin{figure}[ht!]
    \centering
    \includegraphics[width=0.8\linewidth]{img/resultado_act2.jpg}
    \caption{Servo siendo controlado por otro grupo (cliente).}
    \label{fig:resultado_act2}
\end{figure}

\subsection{Actividad 6.2: Cliente remoto con interfaz gr\'{a}fica (socket client)}
\textit{Enunciado: Desarrolle un cliente TCP en Processing que permita controlar remotamente
el servo del servidor.}

En el rol de clientes, se usó \texttt{controlP5} para los controles gr\'{a}ficos y \texttt{processing.net}
para la conexi\'{o}n TCP. Al arrancar, se creó un objeto \texttt{Client} apuntando a la IP del
servidor (la IP del otro grupo) y al puerto que el router tenía redirigido (C\'{o}digo~\ref{lst:cli_setup}).

\begin{lstlisting}[language=Java,
    caption={Creaci\'{o}n del cliente TCP y los controles en \texttt{setup()}.},
    label={lst:cli_setup},
    float=ht!]
import controlP5.*;
import processing.net.*;

Client miCliente;
ControlP5 cp5;
int anguloActual = 0;

// IP del equipo con el Arduino. Puerto: 8080
miCliente = new Client(this, "190.169.74.67", 8080);

cp5.addSlider("slider1").setPosition(50,  50).setRange(0, 255).setSize(150, 20);
cp5.addSlider("slider2").setPosition(50, 110).setRange(0, 255).setSize(150, 20);
cp5.addSlider("slider3").setPosition(50, 170).setRange(0, 255).setSize(150, 20);

cp5.addKnob("Servo").setPosition(500, 60).setRadius(30).setRange(0, 180).setValue(90);
cp5.addKnob("knob2").setPosition(500, 150).setRadius(30).setRange(0, 255);
cp5.addKnob("knob3").setPosition(500, 240).setRadius(30).setRange(0, 255);
\end{lstlisting}

\pagebreak

El env\'{i}o de datos al servidor ocurre \'{u}nicamente desde el callback
\texttt{controlEvent()}, que ControlP5 llama autom\'{a}ticamente cada vez que el usuario mueve
un control. Solo el knob \texttt{"Servo"} genera tr\'{a}fico de red; los dem\'{a}s controles
son puramente visuales (C\'{o}digo~\ref{lst:cli_event}). La comprobaci\'{o}n de
\texttt{miCliente.active()} evita que el programa falle si la conexi\'{o}n se cae.

\begin{lstlisting}[language=Java,
    caption={Envío del \'{a}ngulo al servidor en \texttt{controlEvent()}.},
    label={lst:cli_event},
    float=ht!]
void controlEvent(ControlEvent elEvento) {
    if (elEvento.isController()) {
        if (elEvento.getController().getName().equals("Servo")) {
            anguloActual = (int)elEvento.getController().getValue();
            if (miCliente.active()) {
                miCliente.write(anguloActual + "\n");
            }
        }
    }
}
\end{lstlisting}

En \texttt{draw()} se llama a \texttt{dibujarServo()} para animar el brazo del servo en pantalla con el \'{a}ngulo
actual (C\'{o}digo~\ref{lst:cli_draw}).

\begin{lstlisting}[language=Java,
    caption={Renderizado de brazo del servo en \texttt{draw()}.},
    label={lst:cli_draw},
    float=ht!]
void draw() {
    background(30);
    dibujarServo(anguloActual);
}

void dibujarServo(int angulo) {
    pushMatrix();
    translate(450, 90);
    rotate(radians(angulo));
    stroke(0, 255, 0);
    strokeWeight(4);
    line(0, 0, 40, 0);
    fill(100);
    ellipse(0, 0, 15, 15);
    popMatrix();
}
\end{lstlisting}

\subsection{Actividad 6.3: Interfaz unificada con joystick y servomotor}
\textit{Enunciado: Desarrolle una aplicaci\'{o}n en Processing que integre la lectura f\'{i}sica
de un m\'{o}dulo joystick analógico con el control de un servomotor. El eje X mapear\'{a} \'{a}ngulos de $0^\circ$ a $90^\circ$ y el eje Y de $90^\circ$ a $180^\circ$.
La interfaz gr\'{a}fica debe mostrar los valores ADC de cada eje, el estado del pulsador y una
representaci\'{o}n visual din\'{a}mica del brazo del servo.}

El joystick KY-023 tiene tres se\~{n}ales: dos anal\'{o}gicas de posici\'{o}n (VRX y VRY) y
un pulsador digital (SW). Las primeras dos se conectaron a las entradas \texttt{A0} y
\texttt{A1} respectivamente, y el pulsador al pin digital~2. El servo fue al pin~3, que Firmata maneja como salida
de posicionamiento~\cite{firmata}. El montaje completo se muestra en la
Figura~\ref{fig:circuito_act3}.

\begin{figure}[ht!]
    \centering
    \includegraphics[width=0.6\linewidth]{img/circuito_act3.jpg}
    \caption{Montaje final unificado con Joystick y Servomotor sobre protoboard.}
    \label{fig:circuito_act3}
\end{figure}

\pagebreak

La declaraci\'{o}n de pines y la configuraci\'{o}n inicial en \texttt{setup()} se puede ver
en el C\'{o}digo~\ref{lst:uni_setup}:

\begin{lstlisting}[language=Java,
    caption={Declaraci\'{o}n de pines y configuraci\'{o}n en \texttt{setup()} del sketch unificado.},
    label={lst:uni_setup},
    float=ht!]
int pinVRX = 0;   // Entrada analogica A0 (Controla 0 a 90 grados)
int pinVRY = 1;   // Entrada analogica A1 (Controla 90 a 180 grados)
int pinSW  = 2;   // Entrada digital Pin 2 (Pulsador)
int servoPin = 3; // Pin de control del servo motor

arduino = new Arduino(this, Arduino.list()[2], 57600);
arduino.pinMode(pinSW, Arduino.INPUT);
arduino.digitalWrite(pinSW, Arduino.HIGH);
arduino.pinMode(servoPin, Arduino.SERVO);
arduino.servoWrite(servoPin, 90);          // Posicion inicial segura
\end{lstlisting}

Dentro de \texttt{draw()} se leen los tres valores del hardware y luego se compara cu\'{a}l de los dos ejes se aleja m\'{a}s del
centro de reposo (512 en un ADC de 10~bits) y ese es el que controla el servo. Si gana el
eje~X, el valor se mapea al rango $[0^\circ,\,90^\circ]$; si gana el eje~Y, al rango
$[90^\circ,\,180^\circ]$ (C\'{o}digo~\ref{lst:uni_mapeo}). De esa forma se evita que ambos
ejes compitan y el servo reciba señales contradictorias.

\begin{lstlisting}[language=Java,
    caption={Lectura del joystick y l\'{o}gica de eje dominante en \texttt{draw()}.},
    label={lst:uni_mapeo},
    float=ht!]
valorX   = arduino.analogRead(pinVRX);
valorY   = arduino.analogRead(pinVRY);
estadoSW = arduino.digitalRead(pinSW);

if (abs(valorX - 512) > abs(valorY - 512)) {
    // Eje X domina: rango 0 a 90 grados
    anguloServo = (int) map(valorX, 0, 1023, 0, 90);
} else {
    // Eje Y domina: rango 90 a 180 grados
    anguloServo = (int) map(valorY, 0, 1023, 90, 180);
}
arduino.servoWrite(servoPin, anguloServo);
\end{lstlisting}

\pagebreak

El comportamiento al mover el joystick hacia la derecha (eje X positivo, rango $0^\circ$ a
$90^\circ$) se puede ver en la Figura~\ref{fig:resultado_der_act3}.

\begin{figure}[ht!]
    \centering
    \includegraphics[width=0.8\linewidth]{img/resultado_der_act3.jpg}
    \caption{Prueba de sistema: Respuesta al movimiento positivo en el eje X.}
    \label{fig:resultado_der_act3}
\end{figure}

\pagebreak

La interfaz tambi\'{e}n muestra en pantalla los valores ADC de cada eje y el estado del
pulsador. La funci\'{o}n \texttt{dibujarServoGrafico()} dibuja el brazo animado
(C\'{o}digo~\ref{lst:uni_grafico}).

\begin{lstlisting}[language=Java,
    caption={Funci\'{o}n auxiliar para dibujar el brazo del servo en pantalla.},
    label={lst:uni_grafico},
    float=ht!]
void dibujarServoGrafico(int x, int y, int angulo) {
    pushMatrix();
    translate(x, y);
    rotate(radians(angulo - 90)); // 90 deg apunta arriba en pantalla
    stroke(0, 255, 100);
    strokeWeight(6);
    line(0, 0, 0, -50);     // Brazo mecanico
    fill(255);
    noStroke();
    ellipse(0, 0, 15, 15);  // Eje central circular
    popMatrix();
}
\end{lstlisting}

\pagebreak

El \texttt{delay(20)} al final de \texttt{draw()} introduce una peque\~{n}a pausa para
estabilizar la comunicaci\'{o}n con Firmata y evitar que lecturas muy r\'{a}pidas saturen
el puerto serial~\cite{firmata}. En la Figura~\ref{fig:interfaz_act3} se puede ver la
interfaz completa con todos los datos del ADC y el \'{a}ngulo del servo actualizándose en
tiempo real.

\begin{figure}[ht!]
    \centering
    \includegraphics[width=0.8\linewidth]{img/interfaz_act3.png}
    \caption{Interfaz de usuario final con datos del ADC y ángulo del servo en tiempo real.}
    \label{fig:interfaz_act3}
\end{figure}

\section{Conclusiones}

En este laboratorio se trabajó en extender el control de hardware desde una interfaz local
hacia una arquitectura cliente--servidor usando sockets TCP.

En la actividad~6.1 quedó claro que TCP entrega los datos en orden y sin pérdidas, pero no
separa los mensajes por sí solo. Usar \texttt{'\textbackslash n'} como delimitador junto con
\texttt{readStringUntil()} fue la forma más simple de reconstruir cada comando en el receptor.

En la actividad~6.2 se vio la ventaja de usar el callback \texttt{controlEvent()} para 
solo se enviar datos por red cuando el usuario realmente mueve el knob del servo. 

En la actividad~6.3 se comprobó que la lógica de eje dominante es una solución sencilla y
efectiva para el problema de interferencia entre los dos ejes del joystick, quedándose solo
con el eje que más se aleja del centro.
